# 索引失效优化、独立测量与复盘

2026-11-09。本轮基线为已推送提交 `491f7611579dfc1f52e054dc376c22f89e72394e`，优化源码对应包含本文的提交。实际使用的两个镜像 ID、源码和测量驱动 SHA256 分别写入原始报告。

## 测量先行

新增 `tests/container_benchmark.py` 在宿主机生成 SQL、计算独立 math.dist 真值、驱动进程管道并核对结果。数据库独占 2 CPU、128 MiB、禁用 swap、禁网的容器。每轮新建独立数据卷，同轮重启复用该卷；结束后清理自己创建的容器和卷。

测量包装器只给原有 CLI 增加 stderr 中的快照创建事件，不改变 SQL 和结果协议，不增加查询答案缓存。两个版本使用完全相同的驱动与包装器，报告中的四个驱动文件摘要相同。当前工作区源码与镜像可能不同，因此报告的数据库源码摘要直接从实际镜像读取。

每个版本顺序执行三轮，10,000 条、128 维、1,000 次静态 TopK 查询，K=10，一半按普通列过滤，固定种子 20261112。每轮随后执行六种混合操作，每种 8 次，每次修改或事务操作后立即查询。各轮均逐条核对 ID、数量、顺序、距离；两组召回均为 1.0；重启后逐条核对全部普通列和向量。

报告包含各组延迟中位数、最近秩 p95、往返时间之和、容器累计 memory.peak、memory.events、每个设备 io.stat、CPU 和进程 I/O。查询耗时是 SQL 往返时间之和，不含驱动计算真值与事后校验；不能直接当成正式驱动端到端 T。恢复时间包括 Docker 启动。资源采样中的 sync/cat 小进程也计入容器峰值，未实施宿主机全局清缓存，也没有将多个设备字节相加伪装成正式 B。

## 实现变化与正确性边界

原执行器在每条修改语句开始前清除该表快照，在 COMMIT/ROLLBACK 时清除所有表快照。即使只读事务、零行 UPDATE 或最终失败的 INSERT，也会引起后续重建。

现在在语句内部记录实际变化，成功后再决定失效范围：

- 向量、记录集合或索引元数据变化：清除对应表快照及过滤缓存。
- 普通列变化：保留向量快照，仅清除谓词依赖这些列的过滤缓存。
- 失败语句：先恢复保存点，保留语句之前的有效快照。单客户端执行保证语句中途没有查询读取暂态。
- 零行或相同值更新：保留快照；受影响行数、写入与持久化语义不变。
- COMMIT：事务当前可见状态没有变化，保留有效快照。
- ROLLBACK：按该事务累计实际变更的表/列失效，未修改的其他表保留。

过滤缓存保存的是快照中的位置；记录增删或向量变化仍整体失效。结果投影按主键重新读取当前可见行，不能用保留的向量文件替代普通列状态。重启仍从已提交数据重建。没有改动 WAL 格式、fsync 保证或引入增量向量索引。

## 三轮结果

下表是每组 8 次“操作加查询”累计秒数的三轮中位数，并非单次耗时。

| 场景 | 基线 | 优化后 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 只读事务 COMMIT 后查询 | 0.329223 | 0.105401 | 67.98% |
| 零行 UPDATE 后查询 | 0.341554 | 0.110197 | 67.74% |
| 普通文本更新后查询 | 0.331467 | 0.095169 | 71.29% |
| 过滤列更新后查询 | 0.333249 | 0.146311 | 56.10% |
| 向量更新后查询 | 0.337656 | 0.333433 | 1.25% |
| 部分插入后失败、再查询 | 0.300870 | 0.056532 | 81.21% |

每轮快照创建次数从 **49 降至 9**，逻辑生成量从 **254,800,000 降至 46,800,000 字节**，减少 81.63%。优化后的 9 次包含一次建索引和八次真实向量更新，恢复时另外重建一次，在报告中单列。

必须同时保留未改善的指标：

- 静态 1,000 查询从 3.407834 秒变为 3.511452 秒，慢约 3.04%；本轮没有证明静态查询提速，也不能仅凭这三轮断定原因。
- 数据设备 `8:64` 在混合负载结束后的累计物理写入，两组每轮均为 19,345,408 字节，读取均为 0。逻辑生成量减少不代表磁盘物理写入下降；这些新建又删除的文件可以在写回前由页缓存丢弃。
- 混合阶段容器峰值中位数从 37,543,936 变为 37,588,992 字节，基本相同，没有证据表明整体内存显著减少。
- 写入中位数 3.411109 → 3.083169 秒，恢复（含 Docker 启动）0.650894 → 0.621220 秒。这些不是本轮针对性改动的主要收益，不据此外推正式成绩。

## 复现

下例使用 Bash，Windows 将挂载源改成绝对路径。基线镜像应从上述基线提交另建工作树构建；宿主机始终使用本轮同一个测量驱动。

```bash
docker build --platform linux/amd64 -t minivectordb:r3 .
python -m tests.container_benchmark --image minivectordb:round2-validated --output docs/r3-baseline.json
python -m tests.container_benchmark --image minivectordb:r3 --output docs/r3-optimized.json

docker run --rm --network none --cpus=2 --memory=256m --memory-swap=256m \
  -e TMPDIR=/data -v "$PWD/tests:/app/tests:ro" -v "$PWD/mysqltest:/app/mysqltest:ro" \
  --entrypoint python minivectordb:r3 -m unittest discover -v

docker run --rm --network none --cpus=2 --memory=64m --memory-swap=64m \
  -e TMPDIR=/data -v "$PWD/tests:/app/tests:ro" \
  --entrypoint python minivectordb:r3 -m tests.container_vector_pressure

python -m tests.docker_validation --image minivectordb:r3 --output docs/r3-lifecycle.json
python -m tests.validate_submission --git
```

## 复盘与下一步

先测量再修改使收益可以定位：本轮解决的是“没有必要重建却重建”的额外成本，不是精确距离内核的速度。失败语句和事务边界必须与缓存生命周期一起考虑，只有恢复后的可见状态不变才能安全保留快照。
