# 性能优化验收与回退规则

本项目的优化目标是正确性和约定资源限制始终成立，并让整体表现改善。用户要求避免“一项变快、另一项变慢”：后续不得以局部收益掩盖其他指标的稳定退化。

## 本次发现的问题

1. `b992fa5205eb6110bf25e7b17646b9c02338d556` 把默认行缓存从 16 MiB 缩到 4 MiB。本地单变量实验中，较小缓存降低了内存占用，但首次过滤查询更慢；这说明缓存调整可能造成真实取舍。正式指标由 474 降到 350 的原因尚未证实，不能据此认定缓存是唯一原因。
2. `c13bf4b497d2e150c0053ede9a8205477c584fb1` 的数值结果编码在两组本地对照中改善了纯数值查询；完整字段查询快慢方向不一致，写入耗时波动大。不能将局部收益表述成整体性能稳定提升。
3. 平台目前只提供正式总指标，没有每轮写入、查询、I/O、内存明细；已有说明中的 E 公式与平台展示的数值尺度也不一致。在口径未核实前，不能用自测数值推算正式分数或对平台回退做确定归因。
4. 先前将证据不足的局部改善作为优化候选提交，容易让人误认为综合性能已验证。今后必须明确标识候选状态和未决项；候选提交、测试分支不等于可替换正式参赛基线。

## 每轮必须对照的内容

- **正确性先行**：运行完整回归、官方公开驱动及与改动相关的独立验证；覆盖 SQL、过滤与排序、精确结果、事务内可见性、失败语句、提交、回滚、强杀及恢复。不降低正确性、召回率、持久化或资源限制来换取性能。
- **写入**：从空数据目录开始，按题目基准批量写入并提交；记录端到端耗时。单独核对数据、数量及重启后的持久性。说明输入生成是否计入计时。
- **查询**：至少覆盖 1,000 次 TopK、一半带等值过滤、过滤和无过滤分别统计；增加主键/距离与完整字段两类投影、不同过滤基数及首次/后续查询。核对数量、过滤、ID、顺序和距离，分别计算两组召回率。
- **资源**：分别报告写入和查询场景的端到端时间、整个容器峰值内存、可核实的数据设备物理 I/O，包含索引准备和恢复的相关成本。不能将未核实归属的 `io.stat`、文件大小或进程 RSS 宣称为正式 B 或 M。
- **不同负载**：覆盖题目标准负载和受本次修改影响的边界负载；例如变更缓存要测首次查询与重复查询，变更索引维护要测增删改、回滚及重启。

## 公平比较与判定

1. 记录精确基线及候选 commit、镜像摘要、测试命令、资源限制、数据规模、种子、预热与采集范围。两版保持相同环境和负载，使用独立数据目录；正式基线不得被未提交代码污染。
2. 性能测量不并发运行。至少各运行三轮并交换版本执行顺序；保留逐轮数据，不拼接不同轮次的最佳值。若结果受负载、缓存或执行顺序明显影响，继续隔离和复测，不能直接归因。
3. 对每个指标分别标为改善、无可靠变化、稳定退化或证据不足。没有可靠采集的指标必须标为证据不足；禁止把缺失数据当作无退化。
4. 如任何重要指标出现可复现、超出测量波动的退化，继续调整并复测，或撤销导致退化的改动。不得用另一指标改善抵消后直接称为全面优化。若某项无法有效测量或结果仍不稳定，只能保留为实验候选，不得宣称已满足全面优化验收。
5. 只有正确性与资源检查通过、涉及的重点指标没有可复现退化，并有至少一项可重复改善，才能称为已验证的本地优化。正式表现仍须以平台评测为准；本地通过不代表正式隐藏用例通过。
6. 实验保留原始结果、失败及回退记录，学习材料区分用户真实贡献、Agent 工作和工具输出，不编造结果。遇到官方公式、资源配置或统计口径不明时如实记录；不因缺失数据猜测正式分数。

本规则约束后续优化的本地验收，不改变赛事规则或宣称能够保证正式成绩。已有的正式高分版本应保留，直到新版本获得充分证据。
