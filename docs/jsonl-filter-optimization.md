# JSONL 过滤缓存优化与验证

2026-11-10。基线为 `4f5a5d576c9cf53664d88f7ca4b8226a61e1f99b`；优化版本以本文件所在工作区的源码摘要为准，最终版本以包含它的 Git commit 为准。执行及技术解释由 Agent 完成，不作为学生本人理解的证据。

## 修改

原实现首次查询某个等值条件时，遍历快照并逐条取记录，生成满足该条件的候选位置；查询同列另一个值需重复扫描。第一轮在不同值不超过 128 个、分组在缓存预算内时顺带构造其他值的缓存；后续实验提高到 512 个，并在超限时暂时跳过后续分组尝试。超过阈值放弃分组并沿用原有路径；复杂条件也沿用原路径。缓存仍是派生数据，依赖已有的按列失效与事务处理，不更改持久化或 WAL。

新增回归覆盖：同列其他值复用缓存、过滤列事务更新及回滚、高基数与小预算回退。缓存会保存额外分组，因此可能增加内存；分组构建时同时存在当前选择集合和分组缓冲，瞬时开销不等于缓存本身的预算。

## 本地对照

驱动 [jsonl_benchmark.py](../tests/jsonl_benchmark.py)：2 CPU、256 MiB、无 swap、独立 Docker 数据卷、JSONL 默认入口，每版本各三轮串行；固定种子 20261110，10,000 条 128 维向量、每批 100 条自动提交、200 个 TopK 查询、一半过滤、五个过滤值。查询用 `math.dist` 对 float32 数据构造独立真值，逐条核对 ID 和距离。首次遇到五个过滤值的耗时单独统计。

| 测量项（三轮中位数） | 基线 | 优化后 |
| --- | ---: | ---: |
| 100 次带过滤查询合计 | 0.3263 s | 0.2986 s |
| 五种过滤值首次查询合计 | 0.0824 s | 0.0354 s |
| 200 次查询合计 | 0.6544 s | 0.6719 s |
| 写入 | 4.3199 s | 4.1666 s |
| cgroup memory.peak | 36,716,544 B | 37,330,944 B |

五种过滤值首次查询中位耗时合计下降约 57%，带过滤查询合计下降约 8.5%；总查询耗时本次上升约 2.7%，无过滤项也有波动，因此**不能宣称总体性能稳定提升**。这是一次受固定数据分布影响的本地对照，优化是否改善正式指标需要正式配置及更多测试决定。写入计时包含宿主机生成各批 SQL 的时间，不能直接作为官方写入 T。

每轮在查询后执行 `sync` 并读取 `memory.peak`、原始 `io.stat`，辅助进程计入资源；随后正常关闭。测量不具备官方冷缓存控制、未核实 io.stat 的设备归属和关闭后的完整写回，不能据此计算官方 I/O B 或赛事 E。[基线原始数据](jsonl-filter-baseline.json)、[优化后原始数据](jsonl-filter-optimized.json)保留了逐轮值与镜像 ID。

复现：分别构建基线和修改后的镜像，再用 `python -X utf8 tests/jsonl_benchmark.py --image <镜像名> --output <新报告路径>`。运行会创建并清理自己命名的数据卷；需 Docker Linux 容器。输入和真值在宿主机准备，不计入容器内存。

本节记录的是第一版驱动的实验，原始报告中的 `tests/jsonl_benchmark.py` 摘要对应现归档的 [第一版驱动](../tests/jsonl_benchmark_v1.py)，不是之后扩展参数的当前驱动。

## 扩大分布的对照

延续同一基线和优化版镜像，更新驱动以指定过滤值数量和查询次数。每组均为 10,000 条、128 维、K=10、半数查询过滤、均匀分组；四个场景各有两个版本、各三轮串行。`--groups` 分别为 1、5、100、200，每个过滤值的选中率约为 100%、20%、1%、0.5%。五组场景采用 1,000 次查询，其余为 200 次。每次查询都用独立真值检查完整 ID 顺序与距离，所有轮次通过。

| 过滤值数量（查询次数） | 总查询耗时基线中位数 | 优化后中位数 | 过滤查询基线 → 优化后 | memory.peak 基线 → 优化后 |
| --- | ---: | ---: | ---: | ---: |
| 1（200） | 0.734 s | 0.686 s | 0.371 → 0.356 s | 36,651,008 → 36,818,944 B |
| 5（1,000） | 3.321 s | 3.224 s | 1.452 → 1.382 s | 36,651,008 → 36,978,688 B |
| 100（200） | 1.953 s | 0.589 s | 1.567 → 0.234 s | 36,687,872 → 36,745,216 B |
| 200（200） | 1.902 s | 1.857 s | 1.522 → 1.504 s | 36,642,816 → 36,687,872 B |

100 值场景中基线须对 100 个不同值各自扫描，优化后一次扫描可为其他值填充缓存；当时 200 值超过第一轮 128 个分组上限，回退原路径。由于每种版本分批测量、没有平台冷缓存控制，少量百分比差异不能确定高于环境噪声，也不能推断未知正式数据分布会有相同收益。

原始记录见 [分布矩阵](jsonl-filter-matrix.json)：含 24 个独立轮次、每轮耗时、镜像摘要、源文件摘要、内存峰值及 `io.stat` 原文。未核对设备写回归属，不能将原文作为官方 B，也不能计算 E。复现命令例如 `python -X utf8 tests/jsonl_benchmark.py --image <镜像> --groups 100 --queries 200 --rounds 3 --output <新路径>`。这些对照没有在每轮测完后重启核对全部数据；持久化由下述独立测试覆盖。

## 512 组与高基数回退实验

将上限从 128 增至 512，仍保留分组内存预算；超过上限或预算后，记录有界的表/列标记，数据或该列变化时清除，避免每次查询都再次尝试分组。标记仅影响执行路径，不影响查询结果或持久化。

以下为 10,000 行、128 维、200 次查询、半数过滤、三轮中位数；基线是上一轮 128 组实现，优化为 512 组加回退标记。数据为均匀分组，逐查询核对独立真值。具体逐轮原文、未加回退标记的 512 组中间版本和原始 I/O 见 [实验报告](jsonl-filter-cap-comparison.json)。

| 不同过滤值 | 旧上限总查询 | 新方案总查询 | 说明 |
| --- | ---: | ---: | --- |
| 200 | 1.806 s | 0.418 s | 原实现回退，新方案可缓存分组 |
| 500 | 1.768 s | 0.514 s | 同上；附加缓存占用受预算限制 |
| 600 | 1.937 s | 2.044 s | 三组交替 A/B；新方案仍慢约 5.5% |

600 值场景先前分批测试中未加标记的 512 组相对旧版本慢约 14%，增加标记后分批结果约慢 10%；后续交替 A/B 仍慢约 5.5%。这些数字来自不同轮次，不能严格归因或保证噪声边界，但高基数风险仍存在，不应称为全面提升。高基数分布、更多种子、更新频繁导致标记失效等情况仍须测量；正式数据分布未知，是否用于参赛需要衡量这项取舍。

## 内核距离计算与列值缓存（2026-11-10 第二轮）

上一轮的过滤缓存只在分组成功时有效；600 个过滤值超过 512 组上限后，每次过滤查询仍逐行读取并匹配。本轮同时处理内核与高基数过滤两条路径。

**内核。** 原实现把 8 通道补偿求和直接内联在 TopK 堆循环中。容器内同一数据、同一编译器（g++-12、`-O3 -fno-fast-math -ffp-contract=off`、`target_clones("default","avx2")`）的 A/B 显示：内联补偿版约 1.12 ms/查询，把距离计算提取为独立 `noinline` 函数后补偿版约 0.77 ms，普通双精度 8 通道约 0.44 ms，float32 16 通道约 0.29 ms（每轮 200 次查询、7 轮）。选择普通双精度 8 通道：128 维累加的相对误差约 1e-14，远低于 `vector_index.py` 现有的 1e-12 相对边界保护，无需放宽并列判定；float32 虽更快，但需要把保护阈值放宽到约 1e-5，随机数据下仍可能触发整表 Python 回退，收益与风险不匹配。固定 8 通道的求和顺序与 SIMD 宽度无关，默认与 AVX2 克隆在 `-ffp-contract=off` 下保持逐位一致。实际镜像内 ctypes 调用由约 1.38 ms 降至约 0.49 ms，未过滤查询的引擎耗时由约 1.48 ms 降至约 0.75 ms。

**列值缓存。** 单列等值过滤的首次扫描现在同时保留按快照位置排列的列值列表；分组上限从 512 提高到 4096，仍受同一 1 MiB 缓存预算约束。分组完整缓存时丢弃列值列表（不额外占内存）；分组超限或未全部缓存时保留列值列表，后续查询只需扫描列表而不必逐行 `storage.get`。列值列表、分组和候选位置共用预算，超预算时按 LRU 淘汰；内存受限时列表在构建过程中即被丢弃，不会产生超过预算的瞬时分配。失效规则与原有过滤缓存一致：表或列变化、事务回滚时清除。

**对照。** 10,000 条、128 维、1,000 次查询、K=10、半数过滤，2 CPU、256 MiB、无 swap，JSONL 默认入口；每场景两版本各三轮交替 A/B，查询与真值在宿主机准备，逐条核对 ID 顺序和距离。候选镜像 `sha256:e969b03742e19f09bde5e38ed26626d7f7c71f1f3849b411653df0e8722f06ee`，对照为上一轮候选 `sha256:a9667bc8aa33225842fe7b6cbe52630faff313e1ac0aca2900e56a9542868945`。

| 不同过滤值 | 总查询耗时：上一轮 → 本轮 | 过滤查询 | 无过滤查询 | memory.peak 变化 |
| --- | ---: | ---: | ---: | ---: |
| 5 | 3.482 → 2.962 s（-14.9%） | 1.486 → 1.396 s | 1.997 → 1.547 s | +102,400 B（+0.28%） |
| 200 | 2.866 → 2.216 s（-22.7%） | 1.096 → 0.993 s | 1.770 → 1.223 s | +53,248 B（+0.14%） |
| 600 | 10.441 → 2.672 s（-74.4%） | 8.357 → 1.145 s | 2.084 → 1.527 s | +131,072 B（+0.35%） |

600 值场景的过滤查询首次命中列值缓存后不再逐行扫描，是本次最大收益；5 值场景主要来自内核。写入耗时在本机包含宿主机生成 SQL 的时间（约 1.2 s），两版本差异在噪声内，不能据此声称写入改善。本地 Docker Desktop 的管道往返约占每次查询 1.5–2 ms，会稀释引擎侧收益；正式 T 的驱动开销未知。原始逐轮数据、镜像 ID 与源码摘要见 [内核与列值缓存对照](jsonl-kernel-column-cache-20261110.json)。固定种子、未控制冷缓存、未核实 io.stat 设备归属，不能据此计算官方 B 或 E。

**未采用的改动。** 曾尝试在解析器 `peek` 中跳过 `.upper()`，但 A/B 显示反而慢约 10–15%（短 token 的 `.upper()` 成本低于新增分支），已还原。`DiskHash.replace` 把提交时的 `get`+`put` 合并为一次探测，逻辑等价且回归通过，但单独测量收益在噪声内，只作为减少一次哈希探测的小改动保留。

## 原生向量解析与响应批量写出（2026-11-10 第三轮）

写入路径中每个向量字面量都经过 `json.loads` + `array('f')`，为 128 维向量创建 128 个 Python float 对象。容器内测量显示，10,000 条写入的引擎耗时约 1.18 s，其中向量转换约占 0.3 s。

新增可选原生函数 `mv_parse_vector`：先按 JSON 数字文法严格校验（禁止前导零、`.5`、`1.`、`+1`、NaN/Infinity、尾随字符和 float32 溢出），再用 `strtod` 转换并按 float32 舍入。任何不符合文法的输入返回 -1，调用方回退到原有 `json.loads` 路径，因此接受的语言和错误信息不变。该函数在 MinGW g++ 8.1 和 GCC 12 上均可编译；未编译原生库或使用 `--disable-native` 时完全走 Python 路径。同时把 JSONL 结果行按 64 行分块写出，避免无缓冲 stdout 在大结果集上逐行系统调用。

对照在同一宿主机、独立数据卷、交替 A/B 下进行：

| 测量项 | 上一轮 → 本轮 | 说明 |
| --- | ---: | --- |
| 引擎侧写入（预生成 SQL，仅数据库执行） | 约 1.18 → 0.84 s | 两次交替一致，约 -28% |
| 端到端写入（含宿主机生成 SQL，5 轮交替） | 四次会话均低于上一轮 | 分别约 -11%、-7%、-14%、-19%；绝对耗时随宿主机负载波动 |
| 5 个过滤值、1,000 次查询 | 会话方向不一致 | 一次 2.119 → 1.934 s，另一次 1.902 → 1.971 s，差异在噪声内 |
| memory.peak | 未见增加 | 与上一轮相同 |

端到端写入仍包含宿主机生成 SQL 的时间，不能作为官方写入 T；本地结果也不能计算官方 E。查询侧的原生解析节省约 40 µs/查询，低于本机管道和轮次噪声，因此不能声称查询改善。原始逐轮数据、镜像 ID 和源码摘要见 [原生解析对照](jsonl-native-parser-20261110.json)。新增原生与 Python 的逐位对照及非法输入回退测试；Linux 容器 117 项回归、官方 20 组公开用例和 64 MiB 压力测试均通过。

## 小数据集向量快照驻留内存（2026-11-11 第四轮）

`flat-*.vec` 和 `flat-*.keys` 是可重建的派生索引文件。原实现每次建索引都把全部向量写入磁盘再 mmap；10,000 × 128 维约 5.2 MB，这些写入计入 B，却不增加持久性。

现在按估计大小选择存放方式：估计向量与主键总字节数不超过 8 MiB 时，快照直接构建在 `bytearray` 中，不创建派生文件；超过时沿用原来的文件 + mmap 路径，避免为大数据集申请表大小的匿名内存。构建过程中若实际大小超过上限，也会切换到文件路径。原生内核通过同一地址接口读取两种缓冲，查询路径不变。

对照为 10,000 条、128 维、1,000 次查询、半数过滤，三个过滤基数场景各三轮交替 A/B，逐条匹配独立真值。候选镜像 `sha256:9582cd77740e3c69c3f0029c0d108057ef127d024d306f8ecdb46c2da1c45764`，对照为上一轮 `sha256:3b5e7eb1ba0acc8e0a9bfb74d4496cb5c87d5b874971ffebd4518bfb66a98c46`。

| 不同过滤值 | 数据设备 wbytes：上一轮 → 本轮 | 查询中位耗时 | memory.peak |
| --- | ---: | ---: | ---: |
| 5 | 13,811,712 → 8,609,792 B（-37.7%） | 2.562 → 2.491 s | 36,855,808 → 36,716,544 B |
| 200 | 13,819,904 → 8,617,984 B（-37.6%） | 2.221 → 2.047 s | 36,839,424 → 36,712,448 B |
| 600 | 13,828,096 → 8,626,176 B（-37.6%） | 2.107 → 2.107 s | 37,068,800 → 36,925,440 B |

数据目录文件总量由 12.19 MB 降到 6.99 MB；剩余主要是 WAL（6.20 MB）和可重建的主键索引（0.79 MB）。查询耗时差异在噪声内，不声称查询改善；内存峰值略低。原始逐轮数据、镜像 ID、源码摘要和 io.stat 原文见 [内存快照对照](jsonl-memory-snapshot-20261111.json)。io.stat 的设备归属和完整写回未核实，不能作为官方 B 或 E。64 MiB、18,000 × 1,024 维压力测试仍走文件路径，`oom_kill=0`，耗时 65.64 秒。

## 内核距离归约内联到克隆函数（2026-11-11 第五轮）

上一轮把距离归约放在独立的 `noinline` 函数中，并给它单独的 `target_clones`。容器内剖析显示，内联进 `mv_topk` 后，AVX2 克隆可以把 8 通道归约和扫描循环一起向量化：内核从未过滤查询约 0.493 ms 降到 0.327 ms，`select` 未过滤查询约 0.746 ms 降到 0.457 ms，过滤缓存命中查询约 0.146 ms 降到 0.114 ms。默认克隆仍是可移植的标量路径；没有引入 FMA 或其他新指令依赖。8 通道的固定求和顺序保持不变，默认与 AVX2 克隆在 `-ffp-contract=off` 下仍逐位一致。

早期尝试内联**补偿求和**版本反而慢约 2 倍；本轮内联的是普通双精度版本，A/B 显示内联更快。600 个过滤值的 1,000 次查询交替 A/B 中位由 2.021 s 降到 1.898 s（约 -6.1%）；5 个过滤值的会话受本机管道和轮次噪声影响，方向不稳定，不能据此单独声称总体查询提升。原始数据见 [内联内核对照](jsonl-inline-kernel-20261111.json)。本地结果不是官方 T 或 E。

## FMA 内核与运行时选择（2026-11-11 第六轮）

AVX2 克隆的内核约 0.33 ms/查询。新增一个显式 FMA 归约：两个 `__m256d` 累加器、`_mm256_fmadd_pd`，放在单独的 `mv_topk_fma` 导出中，编译目标为 `avx2,fma`。`mv_has_fma()` 用 `__builtin_cpu_supports` 检查 AVX2 和 FMA，Python 包装层在加载时选择 FMA 或可移植的 `mv_topk`；老库或非 x86 平台自动回退。FMA 的求和顺序与可移植路径不同，结果可能在最后几位不同；Python 的 1e-12 边界保护和 `math.dist` 复算覆盖这一点，返回的记录集合不变。

容器内三次剖析中位数：内核 0.327 → 0.294 ms，未过滤 `select` 0.457 → 0.384 ms，过滤缓存命中 `select` 0.114 → 0.112 ms。1,000 次查询、三轮交替 A/B：5 个过滤值总查询 2.125 → 1.959 s（-7.8%），600 个过滤值 1.993 → 1.867 s（-6.3%），逐条匹配独立真值。原始数据见 [FMA 内核对照](jsonl-fma-kernel-20261111.json)。本地结果不是官方 T 或 E；不支持 AVX2+FMA 的 CPU 使用可移植路径。

## 主键索引按内存限额选择匿名映射（2026-11-11 第七轮）

主键哈希索引是可重建的，WAL 才是权威状态。原实现把它写入 `primary.idx`，并在扩容时写 `.resize` 文件；10,000 行时最终文件 786 KB，扩容中间写入约 1.2 MB，这些写入计入 B 却不增加持久性。

现在读取 `/sys/fs/cgroup/memory.max`：限额至少 128 MiB 或为 `max` 时，索引使用匿名 mmap；否则沿用文件路径。两种模式都在启动时从 WAL 重建索引，匿名模式扩容时分配新映射并重哈希。数据目录在匿名模式下只剩 `database.wal`（6.20 MB）。

对照为 10,000 条、128 维、1,000 次查询、半数过滤，三轮交替 A/B：

| 不同过滤值 | 数据设备 wbytes：上一轮 → 本轮 | 查询中位耗时 | memory.peak |

## 正确性验证与局限

### 单列等值判断优化（中间版本）

对已经绑定类型、只有一个 `=` 的普通列条件，扫描时直接比较行值与绑定值，避免每行调用通用多条件匹配函数；其他条件沿用通用匹配。分组、失效、事务、WAL 规则不变。新增测试比较 BIGINT 单条件与多条件的参考执行路径，并覆盖不存在的值。

以本节之前的 512 组加回退标记版本为基线，同样是 10,000 行、128 维、200 查询、半数过滤、2 CPU、256 MiB、无 swap。每场景三组交替 A/B，每条查询独立检查 float32 真值；完整数据、镜像和源码摘要见 [等值判断对照](jsonl-filter-equality-comparison.json)。

| 过滤值 | 总查询耗时：之前 → 本轮 | 过滤查询耗时：之前 → 本轮 | 峰值内存：之前 → 本轮 |
| --- | ---: | ---: | ---: |
| 600（超过分组上限） | 1.9459 → 1.8791 s | 1.5675 → 1.5129 s | 36,884,480 → 36,618,240 B |
| 500（分组缓存路径） | 0.5896 → 0.6291 s | 0.2376 → 0.2445 s | 36,892,672 → 36,884,480 B |

600 值场景总查询中位下降约 3.4%；500 值场景上升约 6.7%，其中无过滤部分也有波动，尚不能确定原因或排除退化。单个固定种子、三对轮次和未统一冷缓存，不能证明正式综合性能一定提高；原始 io.stat 的设备归属及完整写回未验证，也不能用于计算官方 E。

### 仅对分组超限回退使用快捷判断

由于上述中间版本在 500 值场景有可能退化，最终候选只在单列等值、该表该列已经触发分组超限并被抑制时使用直接比较；正常分组构建与其他表达式继续调用通用匹配。用户数据变更导致标记失效后也恢复通用路径。新增 600 种 VARCHAR 和 BIGINT 值的回归，覆盖标记建立、快捷路径、多条件以及修改后标记失效。

沿用同一数据规模和条件，每场景三组交替 A/B，基线为不使用快捷判断的 512 组方案；逐条核对独立真值。每轮数据、镜像和源码摘要见 [回退快捷路径对照](jsonl-filter-fallback-comparison.json)。
