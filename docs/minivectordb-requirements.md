## 2 SQL 功能与数据语义

对应原说明 2.1、2.2、3.2。

### 2.1 必须支持的功能

| 编号 | 功能 | 验收约束 |
| --- | --- | --- |
| SQL-01 | CREATE TABLE | 支持 BIGINT、VARCHAR(n)、VECTOR(n)；每表一个 BIGINT 主键，最多一个向量列 |
| SQL-02 | INSERT | 支持单行和多行插入；主键不可重复 |
| SQL-03 | SELECT | 支持普通列投影、SELECT * |
| SQL-04 | UPDATE | 支持按主键或条件更新；不要求主键更新 |
| SQL-05 | DELETE | 支持按主键或条件删除 |
| SQL-06 | WHERE | 支持 =、<、<=、>、>= 和 AND |
| SQL-07 | ORDER BY 与 LIMIT | 普通 ORDER BY 并列项按主键升序排列 |
| SQL-08 | L2_DISTANCE | 返回欧氏距离；支持精确 TopK 和带普通列过滤的 TopK |
| SQL-09 | BEGIN、COMMIT、ROLLBACK | 单个显式事务；事务内可读到自身已完成的修改 |
| SQL-10 | 错误处理 | 不支持的语句返回约定错误，不能静默改成其他含义 |

不要求：NULL、JOIN、聚合、子查询、ALTER TABLE、外键、嵌套事务、主键更新。不支持这些语句时仍须正确报错。完整语法、大小写与转义细节、类型边界和错误码须对照题包，不能自行套用完整 MySQL 行为。

### 2.2 字符串与向量

| 项目 | 明确语义 |
| --- | --- |
| VARCHAR 长度 | 按 Unicode 字符数计算，不按 UTF-8 字节数计算 |
| 字符串比较 | 按 Unicode 码点顺序，不做语言相关排序 |
| 向量存储 | 固定维度 float32 数组 |
| 向量输入 | 必须能转换为有限 float32 数值 |
| 必须拒绝 | NaN、Infinity、维度不符、float32 转换溢出 |
| 距离计算 | 基于存储后的向量值；输出允许统一浮点误差，容差以题包为准 |

### 2.3 查询结果顺序

- 未指定 ORDER BY：按集合比较，不要求固定输出顺序。
- 普通 ORDER BY：排序键相同时按主键升序排列。
- 向量 TopK：距离相同时按主键升序排列。
- 过滤 TopK：在满足 WHERE 的记录集合内计算最近 K 条，不能先在全表取 K 条后再过滤。
- 符合条件的记录不足 K 条：返回全部符合条件的记录。
- 空候选集合：返回空结果。

### 2.4 原说明中的 SQL 示例

```sql
CREATE TABLE docs (
    id BIGINT PRIMARY KEY,
    category VARCHAR(32),
    content VARCHAR(1024),
    embedding VECTOR(4)
);

INSERT INTO docs VALUES
    (1, 'database', '事务与恢复', '[1, 0, 0, 0]'),
    (2, 'database', '向量索引',   '[0, 1, 0, 0]'),
    (3, 'travel',   '旅行攻略',   '[0, 0, 1, 0]');

SELECT id, content,
       L2_DISTANCE(embedding, '[0.9, 0.1, 0, 0]') AS distance
FROM docs
WHERE category = 'database'
ORDER BY distance
LIMIT 2;

BEGIN;
UPDATE docs SET embedding = '[0.8, 0.2, 0, 0]' WHERE id = 1;
DELETE FROM docs WHERE id = 2;
ROLLBACK;
```

## 3 向量检索与索引

对应原说明 2.1、2.2、3.2、3.3.1。

| 编号 | 要求 | 说明 |
| --- | --- | --- |
| VEC-01 | 默认 exact 模式 | 精确结果必须正确，不能用近似结果代替 |
| VEC-02 | 显式区分 exact 与 ann | 由测试驱动模式参数控制，具体传递方式待题包确认 |
| VEC-03 | 建立近似索引后仍支持 exact | exact 路径必须返回精确结果 |
| VEC-04 | ann 针对向量 TopK 生效 | 近似索引的正式必做范围以统一题包为准 |
| VEC-05 | 进阶建索引语法 | `CREATE VECTOR INDEX index_name ON table_name(vector_column)` |
| VEC-06 | 算法自行选择 | 不强制 HNSW，但索引核心须自行实现 |
| VEC-07 | 索引维护 | 建索引后新增、向量更新和删除都须正确反映到检索结果 |
| VEC-08 | 事务一致性 | 查询必须反映当前可见记录，回滚后恢复原状态 |
| VEC-09 | 返回合法性 | ID 有效、无重复、满足过滤条件，距离对应当前记录 |

近似检索的真值同样在过滤后的集合内计算。候选集合大小为 N 时，Recall@K 的分母为 min(K, N)；空集合返回空结果，不参与召回率平均。真值中的距离并列按主键规则处理。

性能 benchmark 的有过滤、无过滤两组平均 Recall@10 **分别**须达到 0.95。不能只检查两组合并后的平均值。功能准入中近似检索的具体阈值及范围以题包为准。

## 4 存储事务与崩溃恢复

对应原说明 2.3、3.1、3.2。

### 4.1 持久化与资源约束

- 保存表定义和数据，正常关闭并重启后内容一致。
- 每个正式用例从独立数据目录开始；重启和恢复测试复用该目录。
- 正式测试包含数据量超过内存限额的场景，不能依靠全量加载内存通过所有存储测试。
- 正常关闭时回滚未提交事务并完成必要落盘；关闭信号或命令由题包规定。
- 向量索引允许从持久化记录重建，但必须重建完成后才报告数据库就绪。
- 重建开销计入恢复时间及资源限制。

### 4.2 事务语义

| 编号 | 场景 | 必须满足的结果 |
| --- | --- | --- |
| TX-01 | 未显式 BEGIN 的成功数据修改 | 按自动提交处理 |
| TX-02 | 显式事务内查询 | 普通查询和向量检索均读到本事务已完成的修改 |
| TX-03 | 一条语句失败 | 失败语句不能留下部分修改 |
| TX-04 | 显式事务内语句失败 | 此前成功语句仍可继续提交或回滚 |
| TX-05 | ROLLBACK | 内容、可见记录集合、向量检索均恢复到事务前状态 |
| TX-06 | COMMIT 成功响应 | 响应前必须完成约定持久化，重启不能丢失已确认提交数据 |
| TX-07 | 表与索引 | 不能出现表记录与向量检索可见状态不一致 |

语句原子性与事务原子性都需要满足。实现方案不限定为 WAL、撤销日志或其他特定机制。

### 4.3 崩溃模型

崩溃由强制终止进程产生，不模拟断电、磁盘损坏或外部篡改文件。

| 崩溃前状态 | 恢复后允许的结果 |
| --- | --- |
| 已收到 COMMIT 成功响应 | 必须完整保留提交 |
| 未发出提交请求 | 必须回滚未提交事务 |
| 发出提交请求但未收到成功响应 | 允许完整生效或完整不生效；不允许部分生效 |
| 自动提交语句 | 适用相同的提交确认规则 |
| 恢复途中再次强制终止 | 再次启动仍须正确恢复 |

故障验证不仅要检查记录数量，还要核对记录内容、普通查询、过滤条件与向量检索结果。

## 5 允许依赖与运行协议

对应原说明 2.1、3.1、4.2。

### 5.1 依赖边界

允许通用文件、序列化、数学及 SQL 解析库。组织方可能提供统一解析辅助代码，具体依赖范围随题包公布。

存储、查询执行、向量索引和事务核心须自行实现。不得使用 SQLite、RocksDB 等现成存储或数据库引擎，也不得调用 Faiss、VSAG、HNSWlib 等现成向量索引库代执行。

在 seekdb 仓库提交是交付要求，不能据此推定允许直接使用现成数据库内核完成本题核心能力。

### 5.2 进程与输入输出

- 容器以前台方式直接启动数据库程序，保持同一进程连续处理多条语句和事务。
- stdin 接收 SQL，stdout 只输出协议规定的结果集、状态和就绪信息。
- 日志与调试信息写 stderr，不能污染 stdout。
- stdout 必须及时刷新，避免驱动等待超时。
- 不使用此前示例中的 JSON 请求／响应封装。
- 不通过 TCP 接受测试驱动连接，不需要端口映射。
- mysqltest 风格仅描述脚本与预期文件组织形式，不能直接套用 MySQL 的完整语义。

语句边界、结果格式、错误码、就绪标识、模式切换、正常退出均以 round2 测试驱动和题包为准。预检与正式评测使用同一协议。

### 5.3 容器构建

正式环境为 Linux x86_64。运行期间禁止联网，依赖必须在构建阶段安装完成并锁定版本。基础镜像和依赖版本遵循题包要求。

Dockerfile 必须包含从提交源码构建的完整步骤，或采用多阶段构建。不能仅依赖本地预编译二进制或未交付文件。

以下命令只说明本地启动形式；2 核和 2 GiB 是演示值，不是正式资源限额：

```bash
docker build -t minivectordb:latest .

docker run --rm -i \
  -v minivectordb-data:/data \
  --cpus=2 \
  --memory=2g \
  minivectordb:latest
```

使用 -i 保持 stdin 打开；不使用 -d 或 -t。程序入口和数据目录参数按实际实现配置，所有受统计文件仍统一位于 /data。

| 项目 | 规则 |

| 写入质量 | 核对内容、数量和重启后持久性，不得省略落盘 |

### 7.2 指标统计范围

| 指标 | 定义 | 统计范围 |
| --- | --- | --- |
| T | 平台测量的端到端墙钟时间 | 写入包含全部批次请求、输出与持久化；查询包含正式序列处理和输出，不含统一预热 |
| B | 专用数据设备物理读写字节数之和 | 数据库启动、装载、索引准备、预热、测量结束及相关写回完成 |
| M | 整个数据库容器及其子进程峰值内存 | 与 B 相同的完整过程，包含索引构建峰值和文件页缓存 |

查询装载、索引构建、预热不计入查询 T，但计入 B、M，并受准备时间上限约束。不能将文件转移到未计量目录或外部服务，也不能延迟后台写盘逃避统计。

每轮使用独立容器、cgroup 与数据目录。Linux cgroup v2 通过数据设备 io.stat 的 rbytes、wbytes 增量统计 B，通过 memory.peak 统计 M，禁用 swap；平台需确认文件系统写回归属正常。

基线与选手使用相同硬件、CPU、内存、磁盘及 I/O 带宽配置；冷启动、缓存初始化、预热流程由平台统一。结束后保留 cgroup，完成相关同步与写回统计。镜像构建、评测驱动及事后正确性检查不计入选手开销。

### 7.3 计算公式

写入和查询各有固定基线 T_base、B_base、M_base。基线各指标取三轮测量中位数，参考实现满足相同正确性和持久化要求，查询采用精确扫描。

计算前统一单位，平滑常量为 ε_T = 1 毫秒、ε_B = 1 MiB、ε_M = 1 MiB。

```text
R_T = (T_base + ε_T) / (T + ε_T)
R_B = (B_base + ε_B) / (B + ε_B)
R_M = (M_base + ε_M) / (M + ε_M)

f(R) = R / (1 + R)

E_写入 = 0.6 × f(R_T_写入) + 0.2 × f(R_B_写入) + 0.2 × f(R_M_写入)
E_查询 = 0.6 × f(R_T_查询) + 0.2 × f(R_B_查询) + 0.2 × f(R_M_查询)

E = (E_写入 + 2 × E_查询) / 3
```

三个有效轮次分别计算 E，取中位数后四舍五入保留六位小数，从高到低排名。不能拼接不同轮次最好的 T、B、M。保留六位后相同的 E 并列，E 仅用于排序，不直接计入赛事总分。

总权重：耗时 60%、I/O 20%、内存 20%；写入占三分之一，查询占三分之二。

参考实现、基线、资源配置、统计工具、缓存流程及时间上限须赛前公布冻结。采集不可用或基线异常属于平台故障，不能把缺失指标当作零开销。

## 8 Agent prompt 学习材料与评价

对应原说明 3.4、4.4。规则版本为 `agent-learning-evidence-v3-unbounded`。

### 8.1 文件硬性要求

| 项目 | 要求 |
| --- | --- |
| 文件数与默认位置 | 单个 `agent/conversation.json` |
| 编码与结构 | UTF-8，合法 JSON，顶层对象 |
| 大小 | 不超过 128 KiB；超限拒绝评审，不静默截断 |
| JSON 限制 | 无重复键，无 NaN、Infinity 等非标准 JSON 数值 |
| 版本关联 | 与源码、Dockerfile 纳入同一次提交 |
| 敏感信息 | 不含访问密钥、令牌等；允许脱敏并说明范围 |
| 真实性 | 不得编造交互、实验结果或学生理解；不要求隐藏思维链 |

评审只读取这个 JSON，不自动读取其他仓库文件、外链或平台日志。不能用 Markdown、文本、ZIP 或额外对话目录替代。

可采用 user_prompts、conversations、experiments、retrospective、limitations 等字段，但这些不是强制业务结构。关键证据需直接放入可引用的字符串字段；相邻字段可记录编号、来源、时间、版本。

### 8.2 必须保留的证据内容

- 真实用户 prompt、必要上下文，区分学生、Agent、工具结果。
- 提问调整、实验及反馈，保留理解判断所需前后文。
- 具体实际输出、学生对输出的解释、方案修正、复测与反思。
- 材料范围、脱敏或缺失说明；未执行的工作明确标为计划。
- 联调用合成材料标记 `synthetic: true`，不作为真人学习证据。

外部路径、链接及没有具体结果的“测试已通过”声明不能替代结果证据。Agent 自动给出的规划、解释、代码和修复，不直接证明学生理解；日志本身也不证明学生能解释或运用结果。

### 8.3 五个评价维度

| 维度 | 学生贡献的判断依据 |
| --- | --- |
| 问题理解与自主拆解 | 解释约束、识别难点、有依据地拆解或调整任务 |
| 技术理解与迁移 | 自己解释机制、预测行为，在新场景应用并验证 |
| 独立验证与质疑 | 设计验证、反例、交叉检查，识别建议错误或边界 |
| 实验与反馈迭代 | 参与假设、实验、结果解释、修正和复测 |
| 取舍与反思 | 根据测量解释代价、失败原因、适用条件和局限 |

对话数量、篇幅、模型品牌、调用次数和术语复杂度不加分。简短表达或未反驳 Agent 不自动扣分。

### 8.4 独立实例与分档

每个独立问题、实验或修正链作为一个 unit，只归入最相关维度一次，取最高适用档位。

| 单实例分数 | 所需证据 |
| --- | --- |
| 0.5 | 学生提出具体问题、预测或验证方案，但没有实际结果 |
| 1 | 学生参与验证，并有实际结果 |
| 1.5 | 学生解释结果、据此修正并复测，形成闭环 |
| 2 | 同一实例迁移到新场景、完成验证，并分析局限 |

维度与原始总分均不封顶，但重复记录、换词或拆开同一修正链不增加得分。只有规划时每个真正独立实例最多 0.5 分。泛泛的“继续”“帮我优化”“运行一下”不自动构成实例。

### 8.5 引用与校验

评审报告中，每个实例须给出理由并分别列出：

- `student_evidence`：学生贡献的字符串字段位置与精确原文。
- `result_evidence`：实际结果的位置与精确原文；高于 0.5 分必须提供，0.5 分档必须为空。

引用使用 RFC6901 JSON pointer，例如 `/conversations/0/content`、`/experiments/0/output`，每段精确引用不超过 240 字符。学生贡献和结果不能用同一片段代替，未来计划不能当作结果，同一证据不能重复跨实例或维度计分。

程序校验规则版本、引用位置、原文匹配、档位、重复原文和维度加和；语义上的同一问题或修正链由评审判断。

### 8.6 三轮评审与复核

同一锁定材料独立评审三次，每轮先累计各维度实例得分。

```text
某维度得分 = median(该维度第 1 次分数, 第 2 次分数, 第 3 次分数)
agent_prompt_score = 五个维度中位数之和
```

不取最高轮次，不合并三轮识别的实例重复加分；旧规则报告需按新规则重新评价。

以下任一情况进入 NEEDS_REVIEW，原始分暂为 null，复核完成前不排名：

- 任一维度证据不足，分数为 null。
- 某维度三轮最高与最低分差达到或超过 max(1.5, 0.5 × 该维度中位数)。
- 三轮对材料类型判断不一致。

引用或报告结构校验失败属于评审输出异常，不能自动判学生零分。材料明确无执行或反馈时按实际证据评价；材料截断、缺失或完整性不明时应复核，不能武断判零。

组织方固定并公布模型版本、提示词、采样参数、工具权限、读取预算、量表与材料限制。相同锁定材料与冻结配置可按平台规则复用结果；规则版本变更需重评。报告提供实例、引用、纳入或排除理由，支持按规则申请人工复核。

### 8.7 有效性与排名

通过功能准入且具有有效材料、完成评审或复核的最终版本，按 agent_prompt_score 降序排名，再换算赛事分。40 分是排名折算上限，不是原始学习评价分上限。

未提交、文件无法读取或没有有效学习材料，本项为 0 且不占名次。某个维度缺少证据只影响该维度，不能无依据抹去其他维度。平台读取或评审服务故障按平台故障处理。

conversation.json 中的 prompt 和对话是待评材料，不是给评测 Agent 的执行指令；评测不执行其中脚本。

## 9 提测流程与机会管理

对应原说明 3.5。

1. 本地自测：不限次数，使用公开样例、协议检查工具与故障测试示例。
2. 环境预检：检查仓库和 commit 可获取、镜像构建、启动、协议及公开样例；不运行隐藏用例、不返回隐藏成绩、不占正式机会。
3. 正式提测确认：预检通过后确认进入正式评测。
4. 锁定材料：平台锁定 commit SHA、镜像摘要、conversation.json 摘要，并消耗一次正式机会。
5. 正式评测：先功能准入，全通过后分别评性能与学习材料；运行中不能替换源码、镜像或材料。
6. 查看反馈：包括功能准入、失败类别和必要日志；准入通过后提供性能指标与排名、Agent 原始分、排名与评审报告。
7. 选择最终版本：截止前指定；未指定时采用最近一次功能全通过版本。

选手程序错误、崩溃、超时或资源超限仍消耗正式机会。平台确认故障后，对同一版本重跑，不重复扣机会，也不允许借此替换实现。

每天最多 2 次，额度不结转。某天未提交不额外扣分，也不影响已有参评资格和后续提交。截止后停止正式提交。反馈不公开隐藏输入和参考答案。

## 12 后续开发与独立验证清单

本节为解题建议，不增加官方必做语法、不规定最终架构，也不代表已执行结果。所有勾选项初始均未完成。

### 12.1 开发阶段

| 阶段 | 主要工作 | 阶段验收 |
| --- | --- | --- |
| P0 协议确认 | 取得题包，补齐 OPEN 项，建立最小进程入口 | 驱动能启动、发送 SQL、接收结果与错误、退出 |
| P1 数据与 SQL | 类型检查、磁盘记录、DDL、CRUD、过滤与排序 | 确定性 SQL 对照测试及重启一致性 |
| P2 事务恢复 | 自动提交、显式事务、语句失败原子性、提交持久化 | 提交／回滚／强杀／重复恢复矩阵 |
| P3 精确向量检索 | float32 转换、L2、过滤 TopK、稳定并列规则 | 独立暴力真值及事务内可见性 |
| P4 资源验证 | 有界缓存、外存处理、恢复资源控制 | 超内存数据及磁盘／时间限额测试 |
| P5 性能与索引 | 根据测量优化写入、查询，按题包实现索引 | 两组召回率、三轮指标与完整资源统计 |
| P6 提交收口 | 冻结版本、检查镜像和学习材料、预检 | 同一 commit 的完整交付可复现 |

学习材料随真实开发过程持续记录；不能等到最后再编造学生发言或实验结果。具体存储布局、日志机制、索引算法和语言在确认题包后再决定。

### 12.2 高风险反例

| 验证点 | 建议输入或实验 | 预期检查 |
| --- | --- | --- |
| 多行写入原子性 | 后一行主键重复或向量非法 | 本条语句前面行也未生效 |
| 事务内语句失败 | 先成功修改，再执行失败语句，随后提交 | 只保留此前成功修改 |
| 类型边界 | Unicode 长度边界、float32 溢出、NaN、Infinity、维度错误 | 正确接受或拒绝，失败无残留 |
| 距离存储语义 | 选取转换为 float32 后发生舍入的输入 | 按存储值计算距离 |
| 过滤顺序 | 全表最近记录不满足 WHERE | 返回过滤集合内最近记录 |
| 并列 TopK | 多条等距记录，主键与插入顺序不同 | 以主键升序打破距离并列 |
| 小候选集合 | N 为 0、小于 K、等于 K | 数量正确，召回率分母正确 |
| 索引事务一致性 | 建索引后插入、更新、删除，再回滚 | 普通查询与向量检索恢复一致 |
| exact 路径 | 建近似索引后请求 exact | 与独立暴力真值一致 |
| 提交边界故障 | 请求提交前、提交处理中、成功响应后强杀 | 分别满足三种恢复规则 |
| 重复恢复 | 恢复途中再次强杀，再次启动 | 无部分事务、无重复应用副作用 |
| 超内存数据 | 数据与恢复输入超过配置内存预算 | 不依赖全量内存加载，资源受控 |
| 协议连续性 | 同进程连续多语句、错误后继续输入 | 输出完整及时、stderr 与 stdout 分离 |

其中非法输入的精确表达形式与期望错误码须以题包为准。
