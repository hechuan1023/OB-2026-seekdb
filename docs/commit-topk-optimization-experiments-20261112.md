# 批量提交和 TopK 内核优化试验（2026-11-12）

## 范围和基线

基线为工作区现有主键范围过滤优化，Docker 镜像 `minivectordb:pk-filter-candidate`（sha256:8805f44ab73d407c739c415f6b245fc5c95fd653aea896768775d0f69e9fe887），不是正式版本。保留既有未提交的源码、测试和学习材料。下述两个候选均经测试后回退，现有主键范围优化不受影响。测试在 Docker Desktop Linux，2 CPU、256 MiB、禁网络和 swap，不是官方平台计分。

## 候选 1：提交时只解码主键元信息

假设：提交时建立主键索引仅需表号、主键、删除状态和 WAL 位置，避免对自编码行再次构建完整浮点向量；日志字节和恢复读取路径不变。实现涉及 commit 路径及顺序记录读取器，因可能增加持久化路径复杂度，要求有足够可重复收益才保留。

定向 Docker 测试 21 项通过，包括混合行编码、异常截断、回滚、强杀与恢复、主键过滤；该定向测试验证不了所有故障场景。之后对照 `minivectordb:commit-metadata-candidate` 与基线，每个随机种子各四轮、版本交替，写入和查询分开容器，每轮 10000×128、100 条一批、1000 个 exact 查询、预热 4 条，所有查询逐条核对，写入后独立重启逐条核对。详见 `.local-commit-metadata-20261128.json`、`.local-commit-metadata-20261129.json`。

## 候选 2：一次查询预转换向量数值类型

假设：在 AVX2/FMA 精确扫描中，原路径对每条候选记录反复将相同查询向量 float32 扩展到 double；新路径每次查询预转换一次。存储向量、平方距离计算和求和次序保持不变。非 FMA 路径保持原实现；新增临时 double 缓冲，随维度增加而增加内存。

针对 1、3、7、8、9、31、127、128、129、1024 维及过滤/无过滤随机样本，FMA 两版本的原始位置和距离字节 SHA-256 相同：`2c57c19503c3b68da0d714958c2d72b1373412c7749bc555e45476b0b8061c15`。Docker 向量索引及主键过滤定向测试 29 项通过。这只证明样本和测试，不等于所有浮点输入均已穷举。

同一 seed 20261130、各四轮、完整负载与上述方法相同；基线/候选的写入 T 中位数 1.5979/1.6256 s，查询 T 中位数 1.6496/1.6815 s，写入容器峰值 23.33/23.33 MiB，查询容器峰值 34.66/34.47 MiB；观测写/查 I/O 均分别为 6,086,656/6,037,504 B。逐轮结果见 `.local-query-widen-20261130.json`。查询中位数未改善、轮次差异方向不稳定，**回退该原生候选**，保留基线 FMA 实现。

## 解释和限制

T 为宿主端逐次管道请求测量，不包含平台可能不同的预热和调度；B 为本机容器就绪后到最终 sync 的单设备 cgroup 增量，设备及写回归属未经官方验证；M 为容器累计峰值并含快照辅助进程。各项单独取中位数仅用于本地比较，不混拼成正式 E；不推算排名。既有主键过滤超内存优化的 159 项单测、20/20 官方公开用例和 SIGKILL 恢复回归见 `pk-filter-out-of-core-experiment-20261112.md`。

最终工作区与本轮开始时一样，保留此前的主键过滤优化和用户学习材料；没有将两个缺乏稳定收益的候选加入代码，也没有发起正式提测、提交或推送。下一步应先依据端到端剖析选择更大的性能杠杆，扩展数据投影和缓存状态并持续覆盖 T/B/M 与正确性，而不是按微小单次变化宣称加速。
