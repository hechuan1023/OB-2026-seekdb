# 本轮复盘

本记录由 Agent 撰写，依据实际命令和结果，不代表学生本人已经形成这些解释。

## 本轮解决了什么

此前只有 Windows 正确性与性能记录，Docker 启动失败；这次完成真正 Linux 源码构建、原生库加载、64 项测试、容器 PID 1 退出/强杀恢复、大于硬内存限额的数据验证及 1,000 次向量查询。没有为了通过 Linux 验证改动数据库核心。

官方分支在本轮复查时已有新提交。旧结论“还没有公开测试”必须修正为“已取得首批基础 SQL 样例，尚缺完整协议、驱动和资源基线”。已快进同步该提交，原样执行全部 32 条 SQL，并核对本地协议的列名、记录和受影响行数。公开样例不能替代隐藏准入。

## 发现与修正

- 环境问题：Docker 能启动不等于能从 Docker Hub 拉取镜像。直接拉取超时后改用固定 digest 的已有官方 Python 镜像，构建工具通过可达的 Debian 源安装，所有新增编译包明确锁版本。代价是构建依然需要软件源保留对应版本；正式环境需重新验证可获取性和允许依赖范围。
- 验证器问题：新增资源探针误把元组与列表直接比较，造成假失败。先核对首行内容和执行器返回形态，再改为字段比较，并在新目录重跑。失败输出保留，没有删掉失败后只声称一次通过。
- 内存认识：157 MiB WAL 在 64 MiB 限额中完成恢复与外部排序，但峰值达到上限、发生回收。有限 Python 缓存是必要手段；文件映射和页缓存仍须计入总体资源。该结果支持外存处理可行，不能外推任意数据量/维度/恢复超时都通过。
- 版本一致性：Windows Git 自动换行可能改变已验证文件的 SHA256。对本项目源码、报告和材料指定保留原始字节；提交校验器同时核对工作区、报告摘要、材料版本与 Git blob。

## 性能取舍

已有 Windows 同负载三轮对照中，查询约提升 13.32 倍，写入约提升 3.86 倍；同时增加约 5.2 MB 派生向量文件，恢复中位时间从 0.286 秒增至 0.396 秒，峰值工作集上升。这是减少 Python 逐行计算开销换来的明确收益和代价。

本轮 Linux 单轮不同种子下，1,000 次查询约 2.03 秒、两组召回均 1.0。它验证运行和结果，不足以计算正式 E，也不用于宣称对 Windows 的加速倍数。

精确 flat 扫描避免了当前阶段的近似召回调参，但大数据扫描成本仍线性；高频更新使派生文件反复失效重建。是否引入增量维护或 ANN，应由正式规模、准备时间、内存和查询负载决定。此时继续凭假定协议大改实现，收益不如先补齐官方接口信息。
